# セキュリティチェック1～10の取得元・共通設定設計

作成日：2026-11-03。設計時のコード：v0.10.1 / `04413b2`。

本書は取得設計の見直し案の記録です。実装済みの範囲・連携仕様・検証結果は [v0.10.2の改修内容](security-check-0.10.2.md) を参照してください。[ログイン試行制限の詳細設計](security-check-login-limit-design.md)と併用します。

## 共通の考え方

WordPress内・サーバー/ホスティング側・外部の防御サービス側は、①だけでなく、1～10の情報取得に使う共通の場所として扱います。ただし、各項目で重要な情報は異なります。3か所すべてを必須接続とする設計にはしません。

同じ取得元でも「アプリの処理や欠陥」「防御機能の設定」「観測した通信・遮断記録」は別の根拠です。WAFが有効、遮断件数がある、該当する記録が0件という情報だけで、アプリの脆弱性や侵害の有無を判定しません。

## 項目ごとに利用する情報

「主」は主な確認元、「補」はその項目の確認を補う情報、「—」は通常の設計では使用しないものです。主な確認元であっても、すべての環境でその場所へのAPI接続が必須になる意味ではありません。

| 項目 | WordPress内 | サーバー・ホスティング側 | 外部の防御サービス側 |
| --- | --- | --- | --- |
| ① ブルートフォース | 主：既存の制限機能・適用する認証処理・認証失敗記録 | 主：ログインURLへの回数制限・失敗に応じた遮断設定/記録 | 主：ログイン向けの回数制限・bot対策の設定/適用範囲 |
| ② クレデンシャルスタッフィング | 主：追加認証・利用者/認証経路の設定・認証記録 | 補：入口での制限・認証に関する記録 | 補：利用している外部認証やbot対策の設定/適用範囲。秘密の収集や漏えいパスワードの送信はしない |
| ③ SQLインジェクション | 主：確認できたSQL処理・既知の影響版情報・入力分類 | 補：DBへの権限・分離等の設定、取得可能な関連記録 | 補：SQL攻撃向けルールの設定と分類可能な遮断記録 |
| ④ XSS | 主：出力処理・HTML権限・既知の影響版情報 | 補：配信するセキュリティヘッダー等、取得可能な補助設定 | 補：関連ルールの設定と分類可能な遮断記録 |
| ⑤ DDoS | 補：WordPressまで到達した通信量・HTTPエラー | 主：サーバー負荷・帯域・同時接続・回数制限等の取得可能な設定/統計 | 主：CDN/WAF/DDoS対策の設定、層と対象範囲を区別した通信/遮断情報 |
| ⑥ CSRF | 主：操作ごとのnonce・権限・受付メソッド等の確認 | 補：Cookie・HTTPS・送信元検証等を補う取得可能な設定 | —：一般的なWAFの有無を主判定には使わない。具体的なCSRF対策を取得できる場合だけ追加の根拠にする |
| ⑦ RCE | 主：コード編集/追加権限・実行経路・既知の影響版情報 | 主：PHP等の版・提供元の修正情報・実行制限等の取得可能な設定 | 補：既知の悪用向けルールの設定と関連記録 |
| ⑧ ファイルアップロード | 主：受付処理・権限・許可形式・サイズ等の標準/独自設定 | 主：保存先・実行禁止・読取り/書込み権限等の取得可能な設定 | 補：利用しているアップロード検査や関連ルールの設定/記録 |
| ⑨ 脆弱性悪用 | 主：本体・プラグイン・テーマ等の製品識別と版・更新状況 | 主：PHP/サーバーソフト等、取得可能な構成と提供元の修正情報 | 補：既知の欠陥の悪用を緩和する設定。欠陥自体の修正済み判定とは分ける |
| ⑩ ディレクトリトラバーサル | 主：確認できたパス処理・ファイル参照・既知の影響版情報 | 主：公開範囲・アクセス権限・シンボリックリンク等の取得可能な制限 | 補：関連ルールの設定と分類可能な遮断記録 |

この表は取得する情報の関係を示します。すべての製品・任意の独自コードを自動監査できるという意味ではありません。コード監査を根拠にする場合は、監査対象の製品・ファイル・版を表示し、他製品全体へ広げません。

CSRFの確認はアプリ側のトークン検証や操作受付を中心に扱います。DBへの最小権限やアップロード先の分離も、それぞれコード側の対策と分けて扱います。[OWASP CSRF指針](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html)、[SQL対策指針](https://cheatsheetseries.owasp.org/cheatsheets/SQL_Injection_Prevention_Cheat_Sheet.html)、[アップロード指針](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html)。

DDoSの確認はWordPress到達通信だけに限定せず、サーバーやサービスから取得できるHTTP層・ネットワーク層等の範囲を別々に表示します。HTTP統計を取得しただけで回線全体や全層の耐性を確認したことにはしません。[CloudflareのDDoS保護の範囲](https://developers.cloudflare.com/ddos-protection/)。

## 公開情報との照合は別枠

公式更新情報や既知脆弱性データベースは、このサイトを防御している場所ではなく、取得した製品・版を比較する参照情報です。「外部の防御サービス」のチェックにまとめません。

- ⑨の判定では主要な情報として使います。該当する分類があれば③④⑥⑦⑧⑩等にも、確認できた条件の範囲で関連付けます。
- 公式更新情報・既知脆弱性の照合を行うかを、外部の防御サービスとは別に表示・選択します。送信先、送信する製品情報、取得日時、照合できない範囲を示します。
- 照合には製品・版の取得が必要です。WordPress内の設定/記録の調査を選択しない場合でも、公開照合を選ぶなら比較に必要な構成情報を取得することを明示します。
- 外部の防御サービスが未契約・未接続でも、選択した公開情報の照合を実行できます。照合をオフにした場合は、古い結果を今回の最新照合として利用しません。

## 画面と設定の共有

セキュリティチェック画面の上部に、取得前の共通設定を置きます。

```text
サイト内の情報を調べる場所
  ☑ WordPress内（設定・権限・既存記録）
  ☐ サーバー・ホスティング側
  ☐ 外部の防御サービス側

参照情報
  ☑ 公式更新情報と照合
  ☑ 既知脆弱性情報と照合

選択した場所で必要な接続設定を表示
［再チェック］
```

- 初回はWordPress内を選択します。サーバー・外部防御は利用する場合に選択して接続します。公式更新・既知情報照合は既存機能の設定を引き継ぎ、送信内容を明示します。次回は管理者・サイトごとの前回選択を復元します。
- 接続情報は取得元ごとに1回設定し、①～⑩から共用します。項目ごとのトークン入力や、同じ接続設定の重複保存は行いません。権限と共有範囲は各接続の規則に従います。
- 各項目が必要な情報だけを取得・利用します。外部サービスを選択しただけで、すべての項目の根拠が揃ったとは扱いません。初期画面に30個の必須チェックを並べる構成にはしません。
- 追加設定が必要な取得元だけ入力欄を開きます。選択・入力の後は「再チェック」で検証・保存・取得を行い、保存や接続テストを別の必須操作にしません。
- 全部未選択ならサイト内調査は「調査場所未選択」と表示します。独立して選択した公開情報照合は、必要な構成情報の取得を明示した上で実行できます。実行しなかった調査を正常終了・低リスクとはしません。
- 未選択・未接続・権限不足・通信失敗・未対応・上限到達を分けます。取得できた場所の結果は表示し、失敗した別の取得元で上書きしません。
- 各項目に、今回使った取得元と確認できた範囲を表示します。未選択や取得失敗がある範囲を、サイト全体の安全判定へ含めません。
- 取得場所の選択は調査の選択です。現在稼働している防御設定や、別機能のログ記録・既存集計の有効/無効を変更しません。

## 取得処理の共通化

取得元ごとに「接続状態」と「取得できる情報の種類」を管理します。例えば同じCloudflare接続でも、通信統計の取得成功と、ログイン向けルールの権限不足を別の状態にします。

1. どの項目がどの情報を必要とするかを先に集約します。
2. 同じ取得元の同じデータは1回取得し、各項目から参照します。目的の異なるAPIは別に取得し、取得日時・対象サイト・範囲をそれぞれ保持します。
3. 設定・観測・公開照合・管理者申告を区別した共通形式へ変換します。
4. 各項目は取得済みデータから、その項目について説明できる判定だけを行います。

複数の場所の情報を単純に平均したり、未確認を0点として低にしたりしません。アプリに既知の影響版がある場合、WAFの設定があってもその事実を消しません。記録した攻撃風文字列は、攻撃成立や実際の脆弱性とは区別します。

接続先と送信内容は許可された読取りAPIへ限定します。取得元ごとの秘密情報、権限、応答サイズ、処理時間、再試行回数、保存容量を制限します。外部への送信や追加の取得は、選択と説明の範囲内で行います。API連携がない外部の非公開設定を自動取得できるとは扱いません。

## 現行実装から見直す箇所

- ①：専用の2製品の読取りを中心にする方式から、発見・根拠確認・複数取得元の表示へ移行します。
- ②：追加認証の読取りも現在はTwo-Factor/Wordfence中心です。独自・外部認証を含む経路の発見と、裏付けを取れない理由の表示を①と共通化します。
- ⑤：既存Cloudflare接続を共用しつつ、HTTP統計・WAF設定・DDoS関連の範囲を混同しない取得へ分離します。
- ⑦⑧：現在のサーバー情報の管理者申告を、自動取得の代用にしません。自動取得可能な情報と申告の根拠を別々に保持します。
- ③④⑥⑩：既存のWP Helpers Multiの監査範囲を維持し、他製品や外部防御の情報は根拠を分けて追加します。
- ⑨：公開情報照合を防御サービス接続から独立させ、構成情報の種類・版・対象外の製品・提供元修正の状況を明示します。

実装時は、一つの取得元の失敗・未接続で10項目すべてを一律に未確認へ変えないこと、接続・取得・判定の範囲を分離すること、既存の認証・防御・ログ・更新通知を変更しないことを受入条件とします。
